# 能碳管理平台实质功能审查任务

## 审查目标

本任务用于按《工业企业和园区数字化能碳管理中心评价方案》逐项审查桌面端主要功能。审查重点不是确认页面是否存在，而是确认功能是否对业务用户有实质意义，是否可用、可配置、可编辑、可展示、可计算、可追溯，并识别无意义重复、入口分散和流程不闭环的问题。

前端为主审对象，后端接口、数据模型、演示数据和权限控制作为支撑证据。

## 审查结论口径

| 状态 | 判定口径 |
| --- | --- |
| 有效闭环 | 用户能在页面完成清晰的业务任务，并具备必要配置、录入/编辑、计算/判断、结果展示、处理动作、导出或追溯。 |
| 部分有效 | 页面、数据或接口存在，能支撑部分展示或查询，但缺关键配置、编辑、计算、处置、追溯、权限或跨页面闭环。 |
| 待取证 | 代码、路由或接口显示可能存在能力，但还需要浏览器实测、真实数据、操作结果或截图确认。 |
| 无效 | 纯入口、空数据、报错、半加载、静态样例、无法完成业务动作，或与评价项不构成有效对应。 |
| 不适用 | 当前产品定位或演示范围暂不承接该评价项，需明确边界。 |

## 改造约束

后续整改建议必须遵守以下约束：

1. 不做后向兼容整改，不保留旧页面旁路，不通过新增一套“演示入口”掩盖主流程问题。
2. 多余页面和重复功能优先合并，合并后从菜单、路由和文案上形成唯一主入口；旧入口应删除或重定向到主入口，不继续作为客户可见功能。
3. 非必要不新增后端实体。优先复用现有租户、区域、设备、测点、读数、告警、活动数据、因子、核算批次、报告和审计模型。
4. 非必要不大改后端架构。优先做前端信息架构、页面组合、表单体验、接口编排和少量聚合接口；只有现有模型无法表达业务事实时才立项新增实体。
5. 新增能力必须嵌入现有主线页面，不建设与主线平行的临时页面、临时数据表或临时演示逻辑。

## 实质功能检查维度

每个页面和模块都按以下问题审查：

1. 用户是谁：系统管理员、能源运维、碳核算员、核查负责人、设备运维、经营台账维护人员是否区分清楚。
2. 输入是什么：是否能维护业务对象、基础配置、采集点位、经营活动、活动数据、目标、规则或参数。
3. 业务对象是否清晰：页面是否围绕企业、园区、区域、设备、测点、活动、因子、核算批次、报告、告警、工单等对象组织。
4. 操作是否闭环：是否能新增、编辑、保存、校验、提交、审核、处理、导出、下载或追溯。
5. 数据来源是否清晰：是否能看到 MQTT、电表、导入、手填、第三方接口、计算生成等来源。
6. 计算是否可解释：是否能看到计算对象、口径、因子、单位、时间范围、版本和结果。
7. 结果是否可用：是否有趋势、结构、明细、状态、异常、建议、报告或任务，而不是只有装饰性图表。
8. 页面是否重复：多个入口是否展示同一内容、同一动作是否分散在多个位置、是否存在难以理解的冗余菜单。
9. 权限是否合理：普通业务账号和管理员账号的可见、可编辑、可处理范围是否符合职责。
10. 异常状态是否可处理：空数据、加载失败、权限不足、接口失败、数据质量问题是否给出业务可执行动作。

## 分阶段计划

每个阶段开始前先检查 `progress-tracker.md`。已标为“已闭环”的页面不重复做同类审查；如发现业务范围变化，只在原页面记录中补充变更原因和新增任务。

| 阶段 | 范围 | 评价项 | 目标 |
| --- | --- | --- | --- |
| P1 | 综能监测与数据采集主线 | 1-4, 30-33 | 审查首页、监测中心、告警中心、设备接入、点位监测、电表读数、规则与事件台账是否构成采集-监测-告警-处置闭环。 |
| P2 | 能源运营 | 5-10 | 审查能耗查询、强度计算、用能分析、能效对标、能流、能效平衡是否能从底层数据形成可解释分析和改进动作。 |
| P3 | 微电网、预测、调度和控制 | 11-12, 34-48 | 审查即时控制、场景控制、预测、调度、源网荷储、虚拟电厂相关页面是否具备可配置策略和执行记录。 |
| P4 | 组织碳核算与核查 | 13-14, 25, 31-33 | 审查活动数据、因子、组织边界、核算、审核、报告、凭证、追溯是否形成主线 CRUD 和计算闭环。 |
| P5 | 碳资产、减排与规划 | 15-18, 49-52 | 审查配额、CCER、绿证、行情模拟、履约、减排项目、目标预算、规划结果是否可维护和可解释。 |
| P6 | 产品碳足迹与供应链碳 | 19-29 | 审查 PCF、供应商采集、任务审核、披露、供应链分析是否适合作为主线能力或扩展能力。 |
| P7 | 设备、用户、权限、安全与性能 | 53-74 | 审查设备台账、组织成员、角色权限、多租户、浏览器兼容、性能、安全、审计日志等平台能力证据。 |

## 交付物

- `requirements-matrix.md`：74 项评价要求的页面映射和审查状态。
- `progress-tracker.md`：页面审查、整改、验证、截图和手册状态的唯一进度台账。
- `phase-01-monitoring-data-audit.md`：第一阶段详细审查记录。
- `phase-01-configuration-validation.md`：第一阶段整改后的配置闭环实操验证记录。
- 后续阶段文件按 `phase-XX-*.md` 增量补充。
- 必要时新增 `backlog.md`，把问题拆为前端、后端、数据、权限、文案和信息架构任务。

## 页面流转规则

| 步骤 | 输出 |
| --- | --- |
| 1. 路由和代码审查 | 在 `requirements-matrix.md` 记录评价项映射，在阶段审查文件记录问题。 |
| 2. 实质功能判断 | 判定页面是有效闭环、部分有效、待验证、无效、已合并或不适用。 |
| 3. 整改实施 | 优先合并重复页面、强化主入口、补齐表单和结果态；不建设旁路逻辑。 |
| 4. 浏览器验证 | 记录可操作、可配置、可编辑、可展示、可追溯的实测结果。 |
| 5. 截图和手册 | 复用统一取证脚本补拍结果态截图，并更新操作手册。 |
| 6. 进度归档 | 更新 `progress-tracker.md`，后续任务以该文件为准。 |

## 执行规则

1. 不把页面存在等同于功能完成。
2. 不把静态图表等同于业务计算。
3. 不把超级管理员可操作等同于业务角色可操作。
4. 不把跨页面跳转入口等同于闭环操作。
5. 不把演示数据非空等同于真实可维护。
6. 同类功能重复时必须指出合并或分工建议。
7. 对待取证和部分有效项明确写出补证方式。
8. 整改方案默认删除冗余、合并入口、收敛主流程，不以兼容旧路径作为设计目标。
