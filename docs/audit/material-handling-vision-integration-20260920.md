# 视频识别作业记录与物资碳分摊接入分析

审查日期：2026-09-20。

审查对象：`/Users/eziohelios/Dev/warehouse-forklift`，提交 `5a11076`；同时检查 `litestar-fullstack` 提交 `e59945af` 上尚未提交的物资作业与分摊实现。

本文区分代码现状、已复现问题和建议设计。建议设计尚未实施。本次未修改业务代码、演示数据或线上系统。

## 1. 结论

`warehouse-forklift` 已有视频读取、目标检测、单镜头跟踪、移动状态判定、状态消息、作业时段存储、摄像头配置和统计查询代码。其实际业务粒度是“摄像头中的跟踪目标移动时段”。

它尚未实现物理设备身份、物资编码/批次识别、作业单关联，也没有向能碳平台写入物资作业记录的适配器。因此，现有作业日志不能直接作为已完成物资身份归属的分摊输入。

在“AI 已能输出物资作业记录”的假设下，可以以一条已完成作业为接入单位，补齐设备、物资批次、作业类型和时间，与现有 `MaterialHandlingOperation` 对接。业务模拟可以先行，但不能把模拟通过等同于视觉识别准确率通过。

## 2. 当前链路与实际数据

```text
RTSP / 本地视频
  -> YOLO 检测框、类别、置信度
  -> ByteTrack track_id
  -> 滑动窗口首尾像素位移
  -> Working / Idle
  -> Redis forklift_events
  -> EventListener 内存会话配对
  -> forklift_work_logs
  -> 日/月统计 API

另一路：forklift_realtime -> WebSocket -> 大屏实时展示
```

### 2.1 检测与动作判定

- `src/services/inference_engine.py:66` 调用 YOLO `track()`，使用 ByteTrack；无跟踪结果时调用 `predict()`。
- 本地算法目录不在常规 Git 文件扫描结果中，已额外检查。`algorithm/forkl(DST1523)/data.yaml` 只有 `forklift` 一个类别，`algorithm/model_code/train/args.yaml` 指向叉车检测数据集。不能据此认定已训练物资、托盘编码、行吊、旋转吊、堆垛机或作业动作分类器。
- `models/best.pt` 是指向本地算法目录的软链接，本次确认目标文件存在；未执行模型精度评估。`algorithm/model_code/train.py` 还保留了不同数据集的 Windows 路径，不能视为已经整理好的可复现训练入口。
- `src/services/state_machine.py:75` 只比较窗口首尾中心点距离。移动即 Working；没有载货检测、叉臂动作、库位进出、装卸起止识别。
- 因此空载行驶也可能被算为作业；叉车原地举升、旋转吊固定位置吊装等动作可能被判为 Idle。像素位移不能直接写为米制搬运距离。

### 2.2 消息与持久化

`src/core/event_bus.py:23` 的消息仅含：

| 字段 | 含义 | 不能代表的内容 |
| --- | --- | --- |
| event_type | state_change；另定义 work_session_end | work_session_end 未在实际链路中闭环使用 |
| camera_id | 摄像头标识 | 租户、业务区域、作业设备 |
| track_id | 跟踪目标编号 | 跨镜头/跨重启稳定的资产编号 |
| state | Working / Idle | 入库上架、出库拣选、内部转运、装卸 |
| timestamp | 当前处理时刻的 Unix 秒 | 录像中的原始业务发生时间 |

`src/workers/ai_worker.py:231` 每处理 25 帧发布一次当前状态，不是严格按状态变化发布。注释中的“每秒一次”依赖实际处理帧率，并不保证一秒。

`src/workers/event_listener.py:60` 收到 Working 后，把开始时间放在内存字典；收到 Idle 时取出并计算时长，达到 5 秒才保存。

目前只有三张业务表，见 `src/models/tables.py`：

| 表 | 持久保存的内容 | 缺少的业务关联 |
| --- | --- | --- |
| forklift_work_logs | 自增 ID、camera_id、track_id、起止时间、秒数、创建时间 | tenant、equipment、material、batch、operation_type、任务行、证据地址、模型版本、置信度 |
| daily_statistics | 摄像头每天的记录数和总秒数 | 设备/物资维度；记录数不是物资搬运数量 |
| camera_configs | 视频源、名称、位置文本、启用状态、位移阈值 | 正式区域 ID、设备绑定、租户、身份映射 |

逐帧检测框、识别置信度、状态消息均没有持久化为可追溯记录。日统计存在摄像头+日期唯一键和 upsert；作业日志没有事件去重唯一键。

### 2.3 API、配置与页面

- `GET /api/v1/work-logs` 按摄像头、日期和 offset 查询日志。未提供稳定的增量游标、按更新时间补拉、外部事件接收接口或回写确认接口。
- 摄像头有 CRUD，但 Worker 从命令行/环境变量取配置，没有读取 `CameraConfig`。编辑配置表的阈值或停用摄像头，并不会自动调整已运行 Worker。

- 后端源码中未见租户字段或租户授权处理；能碳平台接入时必须用已认证连接确定租户，不能信任外部 payload 自报租户。

- MSW 可模拟摄像头、日志和统计响应；它不经过识别、落库、设备绑定或分摊链路，不能用作业务闭环证据。

## 4. 能碳平台现有模型能接住什么

`src/py/app/domain/carbon/models.py:622` 的 `MaterialHandlingOperation` 已有：租户、来源系统/来源记录 ID、作业单号、四类作业、起止时间、物资编码/批次/数量/重量、设备 FK、区域 FK、时长、距离、原始来源 JSON。

可以复用该表作为正式作业台账。无需为叉车、行吊等分别建四套作业模型，也无需扩展大量事件类型。

但现有实现仍有以下接入前提尚未满足：

1. **唯一约束不等于幂等接收。** 模型具有 `(team_id, source_system, source_record_id)` 唯一约束，但 `MaterialHandlingOperationUseCase.create()` 直接 INSERT，没有按来源键返回现有记录或更新的接收逻辑；重复请求仍可能抛数据库唯一约束错误。
2. **局部编辑会破坏来源信息。** `_normalize_payload()` 在 PATCH 时仍补默认 source_system、随机 source_record_id、confirmed、measured 和 pcs。仅改备注也会更换来源身份，把草稿转为确认，并重算时长。已用内存对象复现。
3. **设备和区域 FK 已有，物资主数据关联尚未完整。** 当前按 material_code 在 `ProductionProduct` 中补名称/规格，无匹配也可继续；批次只是字符串。不能声称已经验证该批物资真实存在。
4. **未识别物资的观察记录尚不能直接入该台账。** 新增要求 material_code、quantity、equipment_type；需要先留在识别侧待关联，或明确修改现有草稿约束，不能填虚假编码凑齐字段。
5. **重复计算会重复发布 PCF 清单。** 每次执行新建 run；清单来源键引用新的 result.id，所以相同业务输入再次计算可生成另一组 included 清单。demo 先删后建掩盖了这个问题。
6. **目前按设备汇总整个请求期间电量，再按整个作业动因分配。** 不是逐作业时间区间匹配电量；仅与查询窗口相交的小时也整小时计入，跨界作业仍使用完整时长。需要明确期间分摊模式，并处理区间边界。
7. **PCF 研究由调用者统一传入。** 当前会把期间内所有可用结果发布到指定 study，没有按物资批次验证与该产品研究的关系。

上述定位：`src/py/app/domain/material_allocation/usecases.py:40`、`:70`、`:194`、`:241`、`:322`、`:353`。本轮仅审查，没有修改这些逻辑。

## 5. 最小可行的接入与存储设计（建议）

### 5.1 一条作业表达什么

保持一条记录对应“一台设备、一个物资批次、一个动作、一个作业时段”。动作沿用入库上架、出库拣选、内部转运、装卸；设备沿用叉车、旋转吊、行吊、堆垛机。

一个业务任务可以经历多个上述作业；同一物资连续被叉车和行吊处理，应有两条记录。同一任务的暂停/继续观察片段可保留在来源证据中，业务时长采用有效作业时长，不把暂停时间自动算入。

一期演示限定单批次任务。真实现场发生混载时，先标待拆分；不得复制完整时长和重量到多个物资行后全部计算。

### 5.2 摄像头、设备、物资如何关联

| 关联 | 最小实现 | 不能采用的假定 |
| --- | --- | --- |
| 摄像头归属租户/区域 | 接入连接绑定租户，摄像头配置绑定已有区域 | 用 location 文本或来报 team_id 自动授权 |
| 固定设备身份 | 明确单设备监控范围的摄像头/ROI 绑定设备台账 | 一个摄像头覆盖多台设备却固定绑定其中一台 |
| 移动叉车身份 | 可读车身编号/标记，或当前任务明确绑定资产；保存对应识别会话和时间范围 | 把 track_id 当永久资产编号 |
| 物资身份 | 任务行、物资/托盘标识扫码、WMS 单据映射，或可核验的视觉编码识别 | 用最近的入库单、外观类别或相邻检测框直接猜批次 |
| 动作类型 | 从已关联任务类型确定；具备动作识别能力时携带识别依据 | Moving 自动等于入库或装卸 |
| 数量和重量 | 单据明细、称重或已维护单重与数量，记录来源 | 检测到一个框即一件；外观直接估重量 |
| 作业发生区域 | 识别区域/任务地点作为本次作业区域 | 移动叉车的归属部门/停放区域等于每次作业区域 |

固定摄像头绑定可先扩展现有摄像头配置；移动目标映射保存于已有作业来源快照。只有出现独立维护、跨作业复用身份绑定的实际需求，再增加专门的时效绑定实体。

### 5.3 两侧各自存什么

**识别侧：** 扩展现有作业日志，记录稳定 observation_id、摄像头、识别会话、track_id、原始时间/有效时长、结束原因、模型版本、置信度、视频/关键帧引用以及待关联状态。未确认对象身份的记录在此保留。原始帧无需每帧写业务数据库。

**能碳侧：** 复用 `MaterialHandlingOperation` 存经身份归属的作业。设备/区域使用现有 FK，物资/批次保存业务键与快照，`source_payload` 保存识别证据、任务行和关联依据。接入代码负责明确校验，不能把 JSON 当作绕过字段校验的出口。

**接收方式：** 定义一个完成作业的 HTTP 接收契约，复用作业服务。识别侧先持久化，再发送；在现有日志上记录发送结果并重试。能碳侧按租户+连接来源+稳定业务作业行 ID 幂等接收。同一 ID 的相同内容返回原记录；修正通过明确更新处理。实时 Pub/Sub 继续承担展示通知，不能作为唯一业务存储。

业务 operation_id 应来自任务行/已归并作业，observation_id 识别一次摄像头观察。多摄像头对同一任务的观察必须归并成一条业务作业，不能仅靠每个摄像头各自的唯一 ID 防业务重复。

## 6. 从作业到物资碳排放的前提

推荐链路：识别观察 -> 已关联作业 -> 对应设备和期间能源事实 -> 物资批次分摊 -> 经映射的产品碳足迹清单。

1. 设备和电量必须使用同一个台账对象及有效计量关系；有摄像头不等于该设备有独立电表。
2. 固定行吊/堆垛机可以按专用计量回路关联；共享回路缺少设备拆分依据时，不应自动平分。
3. 电动叉车的充电发生时间与作业时间可能不同，充电桩也可能服务多辆车。需要明确充电会话归属及能耗期间；不能把充电桩电量直接当视频片段的即时设备用电。
4. 一期可选择明确的设备班次/期间分摊，先选定可分配电量，再在同一期间完整的已关联作业中按配置动因分配。未识别作业、待机和未知任务的电量应保留未分配部分，不能让少数已关联记录自动承接全部电量。
5. 时长比例、重量乘时长均属于待企业确认的分配假设；没有设备实际负载关系证据时，不能认定重量乘时长更准确。
6. 有效作业时长与视频首尾跨度分开，跨期间按统一时区切分。小时事实与任意时间段只部分重合时，使用更细数据，或限制计算边界并明确估算策略，不能整小时重复算入。
7. 仓储作业分摊结果属于产品系统某阶段的清单输入，不是产品完整碳足迹；必须校验物资批次与研究、阶段、功能单位的对应关系，防止与已有制造电量重复计入。

本节是设计约束，不宣称某种分摊动因为标准强制方法。仓库已有标准研究见 `docs/评价方案/能碳标准与术语知识库.md:84` 中关于 PCF 边界、分配规则、数据质量的记录；本次未另行核验标准现行状态或新增标准公式。

## 7. 正确的 demo 应如何模拟

### 7.1 已有 demo 的真实边界

`woheng.py:3486` 直接构造 8 条作业，`woheng.py:3421` 按额定功率、负载率和分时系数生成小时电量。这能测试基础分配运算，不是摄像头事件接入模拟。

现有样本还有需要修正的地方：

- 每个设备生成 16 小时电量，但只有两条作业，当前计算把整个请求期间电量全部分给这些作业。
- 同设备相邻作业每隔一小时开始，而部分持续 70~90 分钟，造成不同批次任务重叠；样本未解释是否混载或聚合任务。
- 两个租户这部分时间、数量和能量生成参数基本一致，主要变化是标识。
- 生成能源和作业都标 `measured`，虽然来源与备注含演示信息，仍应明确为模拟来源。
- 来源快照没有摄像头、识别会话、任务行、视觉身份关联和可回放证据。
- 所有物资结果发布到电池托盘总成的同一研究，没有逐项产品归属校验。

### 7.2 建议的最小样本

两个沃衡租户均包含四类设备和四类业务动作。使用稳定 fixture ID、固定时钟与固定版本。泰州和湖州采用不同设备数量/作业时长/批次/能耗，但同一校验规则。每条模拟完成作业走实际接收服务，不由演示脚本绕过服务直接写正式作业表。

以单设备的一个完整分摊期间为基础例，假定两条互不重叠作业有效时长为 10 分钟、20 分钟；该期间有 6 kWh 明确可分配电量，且不存在未覆盖作业。采用企业演示假设“按有效时长分摊”：

- A 批次分得 2 kWh，B 批次分得 4 kWh。
- 排放因子使用独立标记的演示配置 0.5 kgCO2e/kWh，则结果为 1 kgCO2e、2 kgCO2e；该值不是对官方因子的声明。
- 同一事件重放两次，仍只有两条业务作业；重复计算可以保留运行历史，但当前有效分摊和 PCF 清单不得翻倍。

只为基础运算设置这个充分覆盖的简单期间。再用独立异常样本检验缺失时是否阻止错误结果，不把缺失数据偷偷补齐。

### 7.3 验收矩阵

| 场景 | 预期 |
| --- | --- |
| 正常完成作业 | 原始识别记录、业务作业、设备、物资批次、能源、结果逐级可查 |
| 重复投递相同作业 | 返回同一业务记录，数量和能碳结果不增加 |
| 修改备注/任务关联 | 保留来源稳定键；不隐式改变确认状态、单位和有效时长 |
| 两个摄像头观察同一任务 | 保留两份观察证据，只有一份业务作业消耗 |
| 同一摄像头重启后 track_id 复用 | 不串到上一条任务；识别会话区分观察 |
| 目标离场/断流 | 保存不完整结束原因，未关联或时长不确定时不算有效完成作业 |
| 识别服务/消费服务重启 | 已持久化观察可以恢复或重放，无重复正式作业 |
| 没有设备身份 | 待关联，不按摄像头或 -1 伪造设备 |
| 没有物资/批次 | 待关联，不按外观或当天单据猜物资 |
| 缺重量但选择重量动因 | 阻止该方法，要求补值或明确改选已批准方法，不静默 fallback |
| 设备无电量/共享电表不明 | 返回明确缺口；不得填模拟能耗冒充现场值 |
| 时区、跨小时/跨日、录像倍速 | 业务发生时间和有效时长稳定，切片不重复 |
| 部分已关联、部分未知任务 | 未知部分不摊给已关联物资；保留未分配能耗 |
| PCF 研究不匹配或重复发布 | 拒绝错配；只保留当前有效清单，不重复计碳 |
| 另一租户的设备/物资引用 | 校验失败，不发生跨租户读取或写入 |

### 7.4 模拟与实测分别验收

- **业务模拟**：假定上游识别已完成，输入确定的作业消息，验证接收、归属、维护、计量关系、分摊、PCF 引用。适合当前先建立正确需求和模型的目标。
- **识别实测**：用人工标注的视频，独立检验设备身份、物资关联、动作边界、漏检/误检、跟踪中断和时间误差。叉车检测模型不能替代另外三类设备的验证。

不把移动方块 MockVideoSource、随机前端图表或直接填充最终分摊结果视为以上任一完整验收。

## 8. 本次验证记录

### 8.1 现有单元测试

原仓库虚拟环境没有 pytest，使用 `uv run --no-sync --with pytest --with pytest-asyncio` 临时依赖层执行，未修改锁文件或项目依赖：

```sh
uv run --no-sync --with pytest --with pytest-asyncio python -m pytest \
  tests/unit/test_state_machine.py tests/unit/test_stats_service.py \
  tests/unit/test_inference_engine.py -q -p no:cacheprovider
```

结果：27 passed，1 failed。失败为 `test_handles_no_detections`：测试只配置 track 的返回值，新增 predict 回退得到未配置 Mock，执行 len(Mock) 报错。它说明回退后的空结果测试未维护好，不直接证明真实 YOLO 对空画面一定抛异常。

现有 `tests/integration/test_event_bus.py` 实际只验证事件构造和序列化，没有覆盖 Redis 投递、监听器重启、落库、设备/物资归属。

### 8.2 定向复现

通过实际 StateMachine、InferenceEngine 提取函数、EventListener.handle_event 运行内存检查；监听器保存函数使用 AsyncMock，未写真实数据库：

| 输入 | 实际输出 |
| --- | --- |
| history_len=5，更新 5 帧 | 实际窗口仍为 25，状态 Unknown |
| 两个无 tracker ID 的检测框 | 两个目标均返回 track_id=-1 |
| Working(100)、Working(101)、Idle(160) | 保存调用 1 次，时长 60 秒 |
| 再重放 Working(100)、Idle(160) | 保存累计调用 2 次 |
| Working 后目标消失 | 内存保留起点，没有保存调用 |
| 新建 Listener 后只收到 Idle | 没有保存调用，原起点已丢 |
| 两个摄像头输入同时间段 | 两次保存调用，没有物理设备去重依据 |
| 能碳侧只 PATCH remark | 来源改 manual、来源键被重建、状态 confirmed、单位 pcs、时长按首尾重算 |

本次没有运行 RTSP/Redis/PostgreSQL 全链路，也没有对视频逐帧标注或测量模型准确率；没有启动图形浏览器验收。关于数据库重复落库的风险由保存调用复现及无唯一约束的模型共同支持。

## 9. 实施顺序

1. 固定一条作业的业务含义、身份来源和可分配能源期间；记录按时长/重量时长选择的企业假设。
2. 修正现有作业服务的 PATCH、接收幂等、设备/物资引用校验、重复发布与期间分摊问题。
3. 扩展现有识别日志的稳定 ID、证据与持久完成状态，补一个完成作业接收适配器；不另建通用事件平台。
4. demo ops 从上游模拟消息开始执行，通过同一接收服务形成正式作业，覆盖两租户、四类设备和异常矩阵。
5. 再完善作业台账列表/详情/编辑/关联补齐、分摊结果与 PCF 引用页面，并实际操作截图补手册。
6. 视觉端逐项补设备身份、任务/物资关联、动作识别和断流恢复，使用标注视频独立验收。

第一批交付以“模拟识别消息 -> 可维护作业台账 -> 设备计量 -> 物资分摊 -> 正确的 PCF 清单”闭环为边界。真实仓库数据质量核验与模型精度验收继续分别记录，避免演示数据替代现场结论。
