# 组织温室气体盘查新体系实施说明

## 2. 实施边界

系统主数据采用 ISO 14064-1 六大类别下的 24 个稳定二级分类，并完整保存 GHG Protocol Scope 1、Scope 2 和 15 个 Scope 3 类别的可逆映射。固定源、移动源、工艺、逸散等术语保留为排放机理或三级活动类型，不与报告分类混为同一层。

底层数据只写入规范化对象：

- `GhgActivityRecord`：活动事实、组织/设施/报告期、分类和原始字段包。
- `GhgEmissionSource`：租户内排放源主档，绑定报告期、组织边界及默认区域、设备或计量边界。
- `GhgActivityAllocation`：活动数据到区域、设备和计量边界的规范化归集关系，保存比例、角色、有效期和名称快照。
- `GhgCalculationMethodDefinition`、`GhgMethodParameterDefinition`：不可变的方法及参数定义。
- `GhgParameterValue`、`GhgParameterAssignment`：参数独立来源、有效期、证据和某次核算的冻结选择。
- `GhgEvidenceFile`、`GhgEvidenceLink`：文件哈希、核验状态及活动/参数/边界/结果关联。
- `GhgCalculationRun`、`GhgCalculationResult`：报告配置、输入、公式、参数和逐气体结果快照。
- `GhgImportBatch`、`GhgImportIssue`：模板版本、文件哈希、预检问题、警告确认和提交状态。

旧 Scope 专用表只在迁移中读取。迁移后没有旧录入 API、旧工作簿入口或双写旁路。

## 3. 分类与方法覆盖

系统登记 11 个方法族。F09 同时提供距离法和运输活动法，因此共有 12 个方法定义。

| 方法族 | 名称 | P0 执行状态 |
|---|---|---|
| F01 | 燃料燃烧热值法 | 已实现 |
| F02 | 活动数据排放因子法 | 已实现 |
| F03 | 碳/物料平衡法 | 定义完成，计算执行待发布 |
| F04 | 工业气体生成与减排法 | 定义完成，计算执行待发布 |
| F05 | 逸散盘存质量平衡法 | 已实现 |
| F06 | 连续/周期监测法 | 定义完成，计算执行待发布 |
| F07 | 生物过程、农业、废物与废水方法族 | 定义完成，计算执行待发布 |
| F08 | 购入能源因子法 | 已实现 |
| F09 | 车辆距离法、运输活动法 | 已实现 |
| F10 | 价值链产品、服务和金融活动法 | 定义完成，计算执行待发布 |
| F11 | 土地与清除碳库变化法 | 定义完成，计算执行待发布 |

未发布的方法不得运行、不得自动退回通用因子法，也不得接受任意 Python、SQL 或上传公式。P0 计算器采用代码白名单；后续发布新方法必须增加方法版本、参数校验和确定性算例。

## 4. 参数与因子规则

活动量、方法参数、排放因子和表征因子分别保存来源。参数值至少冻结：值、单位、来源模式、来源名称/版本、标准及条款、有效期、基准年、地域、技术、燃料或物料、实测方法/机构、质量等级、不确定性和证据编号。

预检强制执行：

- 参数代码必须属于所选方法，参数集内不得重复。
- 参数单位及来源模式必须属于方法定义允许范围。
- 必填参数必须按每个活动引用的参数集完整提供。
- 实测参数必须具备检测方法、检测机构和证据编号。
- 已存在的证据编号只有在 SHA-256 一致时才允许复用。
- 核算必须显式冻结方法代码；不按分类名称推测或回退方法。

## 5. 分类工作簿

每份工作簿绑定盘查任务、组织、设施、ISO 二级分类、报告配置、计算方法和模板版本。工作簿采用统一骨架、按分类裁剪字段：

1. `00_填报说明`
2. `01_组织与边界`
3. `02_排放源`
4. `03_活动数据`
5. `03A_区域设备归集`
6. `04_参数与因子`
7. `05_证据索引`
8. `06_数据证据关联`
9. `07_国家格式对照`（隐藏）
10. `08_校验结果`（隐藏）
11. `09_枚举字典`（隐藏）
12. `_metadata`（强隐藏）

首行为中文业务名称，第二行为稳定字段代码且默认隐藏，数据从第三行开始。模板上下文、必填字段、日期/数值、分类字段、参数定义、证据哈希和关联关系在入库前统一预检。错误阻断提交；警告需要用户明确确认并保留在导入批次中。

## 6. 产品入口与权限

- `/carbon-mgmt/activities`：规范化活动数据台账。
- `/carbon-mgmt/import`：上下文选择、分类模板下载、上传预检、问题查看、确认导入和核算。
- `carbon.inventory.view`：查看。
- `carbon.inventory.import`：下载、预检和提交。
- `carbon.inventory.calculate`：执行核算。
- `carbon.evidence.manage`：维护证据。

所有业务表继承团队隔离模型，并在 PostgreSQL 中启用且强制 RLS。前端只通过生成的 OpenAPI 客户端访问新 API。
请求与响应 DTO 统一使用项目的 `CamelizedBaseStruct` / `msgspec.Struct` 体系，前端直接复用 OpenAPI 生成类型，不重复手写业务响应模型。

## 7. 区域、设备与计量边界归集

区域沿用 `MonitorSector` 的父子树，设备沿用 `MonitorEquipment.sector_id`，购入能源等跨设备汇总使用
`MeasurementBoundary`。盘查领域不复制区域或设备主数据，只保存外键和核算时点快照。归集比例必须大于零且不超过
100%，同一活动的全部有效归集合计必须恰好为 100%。设备归属区域必须等于或位于所选区域的子树中。

24 个二级分类均登记独立归集策略：直接排放通常要求物理发生区域，购入能源要求能源消费或计量归属区域，价值链活动允许按
责任或受益区域归集并保存外部设施，组织层面事项可以归集至根区域。设备字段按分类标记为推荐、条件适用或不适用，不能为了
追求设备粒度而伪造不存在的内部设备。

组织边界发布时必须引用真实区域或设备。核算运行冻结本次使用的区域、设备、计量边界和比例；区域汇总按照叶节点直接值向
父节点逐级滚动，因而同一结果可同时用于设备、区域、园区和租户级统计，但总量只按叶节点归集比例计算一次。

本地仓储租户完整数据通过幂等命令维护：

```bash
app carbon complete-ghg-tenant-data --team default-tenant
```

该命令补齐报告期、发布边界、排放源设备、购电计量边界、全部历史活动的归集关系，以及新体系所需的方法、独立参数和年度
核算运行；重复执行不会新增重复的主数据或同版本核算。新增数据仍应优先通过分类工作簿导入，工作簿中的区域、设备和计量
边界代码来自当前租户主数据下拉选项。
