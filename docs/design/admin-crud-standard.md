# 工业能碳后台 CRUD 页面规范

调研日期：2026-06-13  
适用项目：工业能碳后台，React / Tailwind / shadcn 技术栈

## 0. 目的

本规范用于把后台 CRUD 从“数据库表可视化”提升为“企业业务台账”。所有列表、表单、详情、导入、审计、错误状态应统一。页面不再逐页拼 Card、Tabs 和 Button，而是使用同一套可配置的后台组件。

## 1. CRUD 页面家族

标准 CRUD 包含五类页面或流程：

1. 列表页：查询、筛选、批量操作、导入导出。
2. 详情页：查看对象全貌、状态、关联数据、审计记录。
3. 新增 / 编辑表单：结构化录入、字段校验、草稿保存。
4. 导入流程：上传、映射、校验、预览、提交、错误报告。
5. 审计 / 变更记录：追踪谁在何时改了什么，为什么。

## 2. 列表页标准结构

### 2.1 页面骨架

```
PageHeader
ContextBar / FilterBar
TableToolbar
DataTable
Pagination
DetailDrawer
```

### 2.2 PageHeader

必须包含：

- 页面标题，例如“活动数据台账”。
- 对象说明，一句话，不超过 30 字。
- 主操作，例如“新增活动数据”。
- 次操作，例如“导入”“导出”。
- 可选状态，例如“当前周期已锁定”。

主操作只允许一个。多个高亮按钮会让页面像仪表盘里掉进了圣诞树。

### 2.3 ContextBar / FilterBar

主筛选应优先出现：

- 周期 / 时间范围
- 组织 / 园区 / 车间
- Scope / 排放类别
- 能源介质 / 排放源类型
- 状态
- 数据来源
- 关键字

高级筛选放入折叠区或抽屉：

- 数据质量等级
- 因子来源
- 创建人 / 更新人
- 审核人
- 是否估算
- 是否缺证据
- 是否异常
- 标签 / 业务分类

### 2.4 TableToolbar

工具栏分区：

- 左侧：已选数量、批量操作。
- 中间或右侧：搜索、刷新、列配置、密度切换。
- 右侧：导入、导出、更多。

操作分层：

- 主操作：新增。
- 次操作：导入、导出、刷新。
- 批量操作：批量提交、批量匹配因子、批量归档。
- 危险操作：删除、解除锁定、覆盖导入，进入更多菜单并二次确认。

## 3. 表格规范

### 3.1 密度

建议提供三档密度：

- Compact：后台默认，适合高频台账，行高约 36 到 40px。
- Default：适合包含状态、证据、说明的普通列表，行高约 44 到 48px。
- Comfortable：适合新手或低频页面，不作为默认。

### 3.2 列顺序

通用列顺序：

1. 选择框
2. 对象主列：名称 / 编码 / 批次号
3. 业务上下文：组织、区域、周期、Scope、类别
4. 核心数据：数值、单位、金额、碳排量、能耗
5. 数据来源 / 质量
6. 因子 / 公式
7. 状态
8. 审计字段
9. 操作

### 3.3 数字与单位

- 数值右对齐。
- 单位优先放在列标题，例如“排放量 tCO₂e”。
- 金额、能耗、碳排量、百分比分别使用统一格式化函数。
- 缺失值显示 `-`，不显示 `null`、`undefined` 或空字符串。
- 估算值需要显示标记，例如“估算”badge 或 tooltip。

### 3.4 状态列

状态列使用统一 `StatusBadge`，禁止每页自定义颜色。

通用状态建议：

| 状态 | 含义 | 可操作性 |
| --- | --- | --- |
| 草稿 | 未提交，可编辑 | 编辑、删除、提交 |
| 待校验 | 已提交，系统校验中 | 查看、撤回 |
| 待补正 | 缺失或异常，需要修改 | 编辑、重新提交 |
| 待审核 | 等待审核人处理 | 查看、催办 |
| 已通过 | 审核通过 | 查看、导出、归档 |
| 已驳回 | 审核拒绝 | 查看原因、修改、重新提交 |
| 已锁定 | 进入报告或归档 | 只读、申请解锁 |
| 已停用 | 主数据不再使用 | 查看、恢复 |

### 3.5 行操作

行操作推荐：

- 常用：查看、编辑。
- 次常用：复制、提交、重新计算。
- 更多菜单：归档、停用、删除、查看日志。

操作显隐规则：

- 没权限则隐藏或 disabled，优先使用 disabled + tooltip 说明原因。
- 已锁定对象不可编辑。
- 已通过对象不可直接删除，只能归档或申请解锁。

### 3.6 表格空状态

空状态分四类：

1. 首次创建：提示用户新增或导入。
2. 筛选无结果：提示清空筛选或调整条件。
3. 必要配置缺失：提示先配置组织、因子、模板或权限。
4. 后端失败：提示重试、查看错误详情、联系管理员。

不要只写“暂无数据”。这四个字在企业后台里像一张没地址的便条。

## 4. 新增 / 编辑表单规范

### 4.1 表单布局

表单优先使用分组结构：

1. 基本信息
2. 业务上下文
3. 数据与单位
4. 因子 / 公式
5. 证据附件
6. 审计信息，只读

字段较少时使用 Dialog，字段较多时使用 Drawer 或 Full Page Form。超过 20 个字段时必须分组或分步。

### 4.2 字段规则

每个字段配置应包含：

- label
- name
- type
- required
- unit
- placeholder
- helpText
- validation
- permission
- visibleWhen
- disabledWhen
- auditImpact

### 4.3 单位与换算

- 数值字段必须绑定单位。
- 单位可选时，要显示默认单位和换算关系。
- 计算字段只读，显示公式或 tooltip。
- 涉及 tCO₂e、kWh、Nm³、GJ、吨、万元等单位时，必须使用统一字典。

### 4.4 草稿与提交

表单操作分为：

- 保存草稿
- 保存并提交
- 取消
- 重置

需要审核的对象不应只有“保存”。保存是写库，提交是进入业务链路，两者不能混为一锅汤。

### 4.5 表单错误

错误显示规则：

- 字段级错误显示在字段下方。
- 表单级错误显示在顶部 message strip。
- 导入或批量错误显示为错误表格。
- API 错误要转成用户可理解的业务语言。

## 5. 详情页规范

### 5.1 详情页骨架

```
ObjectHeader
KeyFacts
Tabs / Sections
RightRail
AuditTimeline
```

### 5.2 ObjectHeader

包含：

- 对象名称 / 编码
- 状态
- 版本
- 所属组织
- 主操作：编辑 / 提交 / 审核 / 锁定
- 更多：复制、导出、查看日志、归档

### 5.3 KeyFacts

根据对象类型展示 4 到 8 个关键事实：

- 周期
- Scope
- 数据来源
- 活动数据
- 排放量
- 因子
- 数据质量
- 更新时间

### 5.4 Tabs

通用详情页 tabs：

- 基础信息
- 数据明细
- 因子 / 公式
- 证据附件
- 审核记录
- 变更记录

复杂对象，例如核算批次，应使用更强业务化 tabs：

- 活动数据
- 因子匹配
- 计算结果
- 异常校验
- 证据
- 审核

## 6. 导入流程规范

### 6.1 标准导入步骤

1. 选择模板：系统模板 / 自定义模板。
2. 上传文件：支持 xlsx / csv。
3. 字段映射：源字段映射到系统字段。
4. 数据校验：格式、必填、枚举、单位、重复、权限、锁定周期。
5. 预览提交：显示新增、更新、跳过、错误数量。
6. 执行导入：异步任务，显示进度。
7. 导入报告：成功数、失败数、错误文件下载。

### 6.2 导入错误表

错误表必须包含：

- 行号
- 原始字段
- 原始值
- 错误类型
- 错误说明
- 修复建议
- 是否可自动修复

### 6.3 覆盖策略

导入需要明确：

- 仅新增
- 新增 + 更新
- 覆盖当前周期
- 跳过重复
- 按主键匹配
- 按业务键匹配

涉及已审核或已锁定数据时，必须禁止直接覆盖。

## 7. 删除、归档、停用策略

### 7.1 不建议物理删除的对象

以下对象默认不允许物理删除：

- 核算批次
- 审核记录
- 排放因子
- 计算因子
- 活动数据，已提交或已审核
- 能耗数据，已进入统计
- 证据附件，已用于审核

### 7.2 推荐策略

- 业务数据：归档。
- 主数据：停用。
- 错误草稿：可删除。
- 配置：版本失效。
- 因子：失效并建立替代关系。

### 7.3 危险操作确认

危险操作必须说明：

- 影响对象
- 影响范围
- 是否可恢复
- 是否影响历史核算
- 是否需要权限或二次确认

## 8. 审计字段展示规则

### 8.1 列表页

默认显示：

- 更新时间
- 更新人
- 状态

可选列：

- 创建人
- 创建时间
- 提交人
- 提交时间
- 审核人
- 审核时间

### 8.2 详情页

必须显示完整审计信息：

- 创建人 / 创建时间
- 最近更新人 / 更新时间
- 提交人 / 提交时间
- 审核人 / 审核时间
- 锁定人 / 锁定时间
- 版本号
- 变更摘要

### 8.3 变更记录

变更记录应包含：

- 字段名
- 原值
- 新值
- 操作人
- 操作时间
- 变更原因
- 关联审核单

## 9. 数据质量规则

### 9.1 数据质量等级

建议等级：

- A：自动采集或系统对接，完整且已校验。
- B：人工填报，有证据，已审核。
- C：人工填报，无完整证据。
- D：估算或缺失补齐。
- E：异常或不可用。

### 9.2 质量 badge

数据质量 badge 不等于审核状态。一个数据可以“已审核”但质量为 B，也可以“待审核”但质量为 A。

### 9.3 列表展示

数据质量在以下页面必须显示：

- 活动数据台账
- 能耗数据台账
- 核算批次
- 计算结果
- 报告生成

## 10. 后端字段隐藏规则

页面不应直接暴露以下技术字段：

- 内部数据库 ID，除非排查问题。
- 软删除标记。
- 原始 JSON。
- 后端枚举编码。
- 系统内部任务 ID。
- 租户 ID。

但这些字段可以在“技术信息”折叠区向管理员展示。

业务字段必须使用业务语言：

- `org_id` 显示为“组织”。
- `factor_id` 显示为“排放因子”。
- `activity_value` 显示为“活动数据”。
- `quality_score` 显示为“数据质量”。
- `calc_batch_id` 显示为“核算批次”。

## 11. 组件实现建议

### 11.1 全局组件

建议沉淀：

- `AdminPageHeader`
- `ContextBar`
- `FilterDrawer`
- `DataTable`
- `TableToolbar`
- `ColumnVisibilityMenu`
- `StatusBadge`
- `QualityBadge`
- `AuditFields`
- `AuditTimeline`
- `ImportWizard`
- `EvidenceUploader`
- `FactorSelector`
- `CalculationTrace`
- `ObjectDetailDrawer`
- `EmptyState`
- `ErrorState`

### 11.2 Schema 驱动

建议把每个台账配置成：

```ts
export type LedgerPageConfig<T> = {
  objectName: string
  route: string
  primaryKey: keyof T
  filters: FilterConfig<T>[]
  columns: ColumnConfig<T>[]
  actions: RowAction<T>[]
  batchActions: BatchAction<T>[]
  importConfig?: ImportConfig<T>
  auditFields?: AuditFieldConfig<T>
  emptyStates: EmptyStateConfig[]
}
```

这不是为了把产品做成低代码平台，而是为了保证同类页面同一种骨架。

## 12. CRUD 验收清单

列表页：

- 是否有统一 PageHeader？
- 是否有主筛选和高级筛选？
- 表格列顺序是否符合规范？
- 数值是否右对齐并显示单位？
- 是否使用统一状态 badge？
- 是否有批量操作？
- 是否有导入导出？
- 是否有列配置和密度切换？
- 是否有空状态、错误状态、无权限状态？
- 是否能打开详情 drawer？

表单：

- 是否分组？
- 是否区分保存草稿和提交？
- 是否有单位和字段校验？
- 是否有证据附件？
- 是否隐藏技术字段？
- 错误是否可理解？

详情：

- 是否有 ObjectHeader？
- 是否有 KeyFacts？
- 是否显示审计字段？
- 是否有变更记录？
- 是否能查看证据、因子、公式、计算追踪？

导入：

- 是否支持字段映射？
- 是否有预校验？
- 是否有错误下载？
- 是否保护已审核和已锁定数据？

删除 / 归档：

- 是否区分删除、归档、停用、失效？
- 是否说明影响范围？
- 是否有二次确认？
